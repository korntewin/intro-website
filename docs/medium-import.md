# Publishing the RIIR article on Medium

## Import URL

After the GitHub Pages deployment completes, use this URL in Medium **Stories > Import a story**:

https://korntewin.github.io/intro-website/blog/riir-rust-prediction-service/medium/

The original article includes a **Medium import view** link above its title. The import view is generated by `npm run build` from the finished article HTML, so changes to the Markdown automatically reach both views. It is available through `npm run preview` after a build, rather than the development server.

Check the new draft for all 15 images, captions, Thai text, comparison paragraphs, and code blocks. This includes the Prediction Service Direction diagram in the “Why Rust” section. Check that Medium's canonical-link setting points to the original article:

https://korntewin.github.io/intro-website/blog/riir-rust-prediction-service/

The import view declares that canonical URL and `noindex,follow`, but Medium's resulting draft settings still need to be checked. A fresh import tests the new source; an existing draft is not evidence that the updated page was fetched.

## What was actually wrong

Before this fix, the deployed page already had 14 valid, publicly accessible PNGs with absolute HTTPS sources, explicit dimensions and eager loading. The previous absolute-URL and figure-markup changes were deployed. Missing files, SVG sources, relative paths and lazy placeholders were not the current problem.

The layout declared an `h-entry` with a title, publication date and summary but omitted its `e-content` property. A microformats2 parser therefore extracted those three fields with **no full content or inline images**. Wrapping the complete Markdown body in `e-content` makes a standards-based parser extract the article HTML and all 14 images. The body also carries Schema.org's `articleBody` property:

```html
<article class="h-entry" itemscope itemtype="https://schema.org/BlogPosting">
  <h1 class="p-name" itemprop="headline">Article title</h1>
  <p><time class="dt-published" datetime="2026-10-23">2026-10-23</time></p>
  <p class="p-summary" itemprop="description">Article summary</p>
  <div class="e-content entry-content" itemprop="articleBody">
    <!-- Complete Markdown body, including every paragraph, image and caption. -->
  </div>
</article>
```

This is a reproduced structured-content extraction defect, **not a reproduction of Medium's private importer**. Medium documents that a third-party API interprets the URL on its behalf. We cannot inspect that service's decision for this article or promise that HTML changes alone guarantee its success.

## Plain import representation

`scripts/build-medium-import.mjs` reads the built article and generates `/blog/<slug>/medium/index.html`. It preserves the title, date, summary, full body, image positions, captions, links, and code whitespace. Navigation, theme controls, reading progress, scripts, Astro islands, and site styles are omitted.

Figures become conservative HTML that extractors can retain:

```html
<p><img src="https://korntewin.github.io/intro-website/blog/figures/riir-cover.png"
        alt="Article cover" width="1800" height="763"></p>
<p><em>Article cover</em></p>
```

The normal article keeps its semantic figures and existing design. Cover-image and publication-date metadata are also exposed in the page head. The two comparison tables continue to render as six labeled paragraphs, with their original values and formatting.

Embedly's public extraction documentation lists `p`, `img`, and `em` among its supported content tags, while `figure` and `figcaption` are absent. Its cache documentation also describes URL-based caching. These are compatibility references, not proof that Medium currently uses that provider or that a figure wrapper caused this failure. A distinct import URL supplies a fresh fetch target without changing the original article URL or its images.

## Verification

- `npm test` checks image URL normalization, existing figure/table transformations, and the plain export's content preservation, image order, links, code whitespace, and removal of client-only markup.
- `npm run build` runs those checks, creates PNGs and the ZIP, builds Astro, generates the import view, then validates both outputs.
- `npm run check:blog-html` verifies that all source images and story sections are inside the complete `e-content`; image bytes and dimensions match; and the original and import views preserve text, image positions, code, and the original canonical URL.
- Both existing GitHub Actions workflows run `npm run build` and therefore enforce these checks.

The original and import pages must expose all 15 current images to a microformats2 parser. Passing these checks verifies the website's output, not a successful Medium draft. End-to-end confirmation requires a fresh import on Medium after deployment.

## If Medium still drops an image

Medium's documented fallback is to copy the rendered content into a draft and upload missing images. The existing [PNG ZIP](https://korntewin.github.io/intro-website/blog/medium-images.zip) contains all 15 files numbered in reading order. Upload missing images individually to avoid Medium's multi-image grid, and keep the canonical URL set to the original article.
